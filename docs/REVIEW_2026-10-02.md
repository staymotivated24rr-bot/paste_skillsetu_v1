# SkillSetu product & engineering review — 2026-10-02

## Scope

Reviewed the current `main` implementation and deployment configuration for the complete student flow, workplace simulations, scoring/gap logic, targeted learning, practice/mastery, reassessment, readiness reporting, fictional placement dashboard, responsive/accessibility behavior, API security, persistence, maintainability and test coverage.

The deployment is reported by GitHub/Vercel as successfully built. Direct interactive browsing of the Vercel URL was not available from the review environment, so runtime findings are based on source inspection, automated browser coverage already present in the repository, CI verification, and the deployment configuration itself.

## Priority findings

### P0 — hosted persistence was unsafe on Vercel

**Finding:** production used `file:./dev.db`, which is correct for local development but is not durable application storage for serverless deployment. The student journey writes users, attempts, answers, lesson progress and reports, so a local file database is not suitable for the public deployment.

**Fix on this branch:**
- added hosted libSQL/Turso support while keeping local SQLite unchanged;
- added `setup:hosted` and a hosted migration runner;
- added `/api/health`;
- Vercel with only a `file:` database now returns a clear 503 instead of pretending writes are durable;
- documented the exact hosted deployment flow.

**External action still required:** create a durable libSQL/Turso database, set `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` in Vercel, run `npm run setup:hosted`, then redeploy.

### P1 — pilot access is demo-grade, not production identity

**Finding:** student access uses a random HttpOnly demo cookie and the placement dashboard is intentionally public fictional data. This is reasonable for a product demo, but it is not sufficient identity, authorization or multi-tenancy for real college records.

**Not changed automatically:** choosing authentication, college tenancy and retention policy is a product/privacy decision. Before collecting real student data, add authenticated identities, placement-officer authorization, consent/retention rules and an account/session recovery strategy.

### P1 — public deployment can be spammed

**Finding:** anonymous users can create demo sessions repeatedly. Same-origin checks and input limits reduce browser abuse, but there is no durable rate limit or invite gate.

**Not changed automatically:** an invite code, Vercel protection, identity provider or database-backed rate limiting would materially change pilot access. Select one before a public real-student pilot.

### P1 — repository visibility is public

**Finding:** GitHub reports `staymotivated24rr-bot/paste_skillsetu_v1` as a public repository. No committed secret was found in reviewed configuration; `.env` and SQLite files are ignored. Still, if the founder intended the project to remain private, repository visibility should be changed in GitHub settings.

### P2 — diagnostic evidence density is too low for strong skill claims

**Finding:** the 16 Data Analyst skills currently have only about 1–6 mapped diagnostic actions per bank. A skill with one item can jump between 0 and 100, so the result is useful as prototype guidance but not a validated employability measure.

**Not an engineering-only fix:** increase independent evidence per important skill, add alternate item banks and validate rubrics with analysts/placement staff before making stronger claims.

### P2 — diagnostic is applied but still recognition-based

**Finding:** the simulations are significantly better than a textbook quiz: they use realistic stakeholders, case data, follow-ups and applied decisions. However, answers are still structured choices. They do not prove the learner can independently write SQL/Python or compose a free-form stakeholder response.

**Next validation:** add independently scored fresh tasks (human-reviewed at first) before introducing AI free-form grading.

### P2 — architecture is still hard-coded to one role

**Finding:** service queries and UI labels currently hard-code `data-analyst`. This is acceptable for the original one-role MVP but will become a maintainability problem when Python Developer and Java Developer are added.

**Recommendation:** make role ID part of session/attempt context and drive role skills, assessments, lessons, employer profiles and cohort views from data rather than scattered conditionals.

### P2 — no CI existed for future regressions

**Fix:** added GitHub Actions verification for clean install/setup, typecheck, lint, production dependency audit, unit/integration tests and production build.

### P2 — baseline browser navigation semantics could be stronger

**Fix:** added `aria-expanded`, `aria-controls`, dynamic navigation labels and `aria-current` on active navigation items.

### P2 — basic response hardening was missing

**Fix:** added safe baseline headers: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` and a restrictive `Permissions-Policy` for camera/microphone/geolocation.

### P3 — persistence copy was misleading after deployment

**Fix:** changed “Progress saved locally” / “Local-first prototype” wording so the interface remains accurate whether running locally or with hosted storage.

## What is already strong

- Three realistic diagnostic cases with 24 scored actions and three distinct reassessment cases.
- Server-side answer keys and grading; future responses/keys are not sent to the client before answering.
- Scores derive from submitted responses; practice does not silently inflate diagnostic scores.
- Prerequisite-aware gap ordering and importance-weighted readiness.
- Original lessons with both interactive and structured modes, hints, retries and first-response mastery logic.
- Honest reassessment declines are supported.
- Ownership checks prevent one demo session from writing another learner's attempt.
- Input validation, request size guard and same-origin browser submission check are present.
- Mobile, keyboard, refresh/resume, report printing and API abuse cases already have Playwright coverage.
- Fictional cohort data is explicitly separated from actual student sessions.

## Pilot readiness

**Not ready for a 20–30 student pilot on the current public Vercel deployment until durable hosted storage is configured.**

After hosted storage is configured, the product is suitable for a **controlled prototype/UX pilot using nicknames and no sensitive student records**. It is not yet suitable for a production college rollout or for claims that the readiness score predicts employment.

Before a higher-stakes pilot:
1. configure durable hosted storage;
2. restrict access or add rate limiting;
3. freeze/version the assessment content;
4. add more independent evidence for important skills;
5. have at least one analyst and one placement professional review the rubric;
6. use fresh externally scored transfer tasks to evaluate whether learning gains generalize.

## Recommended next build order

1. Finish durable production persistence and verify the live journey.
2. Refactor the role model before adding Python Developer and Java Developer.
3. Add controlled pilot access.
4. Increase/validate diagnostic evidence.
5. Add free-form or executable tasks only after a reliable scoring rubric exists.
6. Use pilot evidence to decide whether voice/avatar conversation improves measurement enough to justify its complexity.
