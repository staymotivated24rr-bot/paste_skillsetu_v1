# SkillSetu authentic readiness implementation report

2026-10-02 · branch `feat/python-authentic-readiness` · prototype evidence, not employment certification.

1. **Executive summary.** Python Developer now uses executable browser tasks, authored workplace decisions, ordered workflows, deterministic explanations and transfer checks. A shared dark interface, evidence reports and deeper repair loop replace the thin diagnostic experience. Data Analyst and Java retain their existing content and independent histories.

2. **Product problems fixed.** The diagnostic no longer depends entirely on recognition questions. Skill conclusions disclose evidence diversity; learning completion cannot inflate readiness; historical reports retain their assessment version; an improving average can honestly coexist with declining skills and new gaps.

3. **Architecture changes.** `src/lib/authentic` contains typed banks, public projections, grading, evidence analysis, repair planning and persisted services. Shared task rendering supports six task types. Python gets the new content first; role-specific legacy runners remain available for Data Analyst, Java and historical Python attempts.

4. **Database migrations.** `202610020003_authentic_evidence` adds bank, task evidence and repair tables plus nullable/default-compatible attempt and score fields. Previously applied migrations are unchanged. Repeated setup preserves exact sealed answers, scores and repair records. No production migration, reset or deletion was performed.

5. **Python authentic-assessment design.** Each published bank has 68 tasks, four fictional workplace contexts and 17 skills. Every skill receives four unaided opportunities; debugging, testing, reasoning, exceptions, functions, data structures and validation receive at least six mapped opportunities. A task has at most three skill mappings with explicit weights. The estimate is 90–120 minutes, with refresh/resume supported.

6. **Task types implemented.** Workplace decision, executable code edit, executable bug fix, deterministic short answer, ordered steps and transfer. Each bank contains 17 decisions, 17 ordered workflows, 26 coding tasks and eight explanation tasks. Transfer uses code or explanation according to the skill.

7. **Python sandbox design.** Pinned Pyodide 0.29.3 assets are self-hosted. Each run creates an opaque-origin iframe with `allow-scripts` only and a disposable Web Worker. CSP limits asset loading to `/python/`; runtime network primitives and nested workers are disabled. Execution terminates after five seconds following runtime initialization, with a separate 60-second loading limit. Server grading compares submitted JSON outputs; it never executes learner Python.

8. **Sandbox security limitations.** Browser execution transcripts can be inspected and forged. Import and builtin restrictions provide defense in depth, not a certified Python security sandbox. There is no hard browser memory quota or high-stakes proctoring. A malicious learner may bypass prototype evidence integrity; this cannot establish employability. Production credentials, server filesystem and shell are never placed in the browser runtime.

9. **Evidence/confidence model.** Limited, Moderate and Stronger evidence depend on opportunity count, task diversity, contexts, independence and transfer. Correctness affects proficiency, not evidence breadth. Repeated identical task IDs do not inflate cumulative diversity. Labels are descriptive and explicitly not statistical confidence intervals. Legacy recognition-only evidence remains limited.

10. **Scoring changes.** Coding receives case-level partial credit; decisions receive binary credit; ordered workflows use pairwise ordering; short answers use visible dimensions and deterministic concept groups. Weighted task evidence produces skill scores; role importance produces overall readiness. Latest completed assessment determines current proficiency, with stored skill targets and weights. Actual improved, declined, unchanged, newly measured and newly below-target skills explain changes. The browser acceptance measured 57% → 69%, 11 improved, four declined, two unchanged and two new gaps (classes/composition and technical communication).

11. **Adaptive stakeholder system.** Authored strong, developing and risk responses reflect the submitted evidence. A previous response reveals a conditional stakeholder constraint on the next task. Task count and grading contract remain fixed to preserve bank comparability. This is an authored conditional simulation, not an autonomous AI conversation or a branching task graph.

12. **Assessment bank/versioning system.** Two baseline and three reassessment banks rotate within their kind, avoiding immediate reuse where alternatives exist. Current IDs end in `v2.2`, assessment version is `python-authentic-v2`, content version is `2026-10-02.3`. Stored content and SHA-256 digest prevent seed-time mutation. Attempts retain selected bank, role/skill snapshots and immutable submitted evidence. Archived banks remain usable by their original attempts.

13. **Learning repair-loop improvements.** Seventeen Python modules include concept, intuition, worked example, guided problem, independent problem, harder application, workplace task, verification, transfer and interview reflection. Structured and interactive modes share persisted progress. Hints, retries and first responses are recorded separately. Mastery requires five of six strong first responses including transfer; retries teach without overwriting first-response evidence. Practice cannot change assessment readiness.

14. **Personalized 7-day plan.** Prerequisite-ordered gaps and module effort distribute repair across six days; day seven requests fresh reassessment evidence. Mastered modules leave the pending queue; day seven budgets 120 minutes for the fresh assessment. Priority #1 includes failed evidence examples, target, reason, prerequisites, effort and workplace value. This is a suggested plan, not a guaranteed seven-day outcome.

15. **Transfer-evidence implementation.** The fourth assessment context applies the skill in a different workflow, and every repair module ends with a transfer challenge. Evidence records retain the transfer flag; reports show its contribution to evidence strength. Fresh-bank reassessment measures assessed proficiency separately from practice.

16. **Dark premium UI redesign.** Semantic tokens use near-black and charcoal surfaces, off-white text, muted gray and restrained emerald. The compact sidebar, focused workplace task, developer code surface, skill map, obvious repair priority and calm cohort cards share the same system. Print switches to white paper and dark text.

17. **Accessibility/responsive changes.** Visible focus, labeled fields, fieldsets, keyboard radio choices, accessible order controls, reduced motion and mobile drawer focus trapping/restoration are implemented. Coding on small screens includes larger-screen guidance while preserving drafts. Reports are tested at 1440, 1024, 768 and 390 pixels; mobile workspace and task views also have overflow assertions. Core text and accent tokens exceed 6:1 contrast against the lightest standard surface (muted text 6.06:1; primary text 13.89:1). This is targeted browser coverage, not a complete WCAG audit.

18. **Readiness report improvements.** Reports expose per-skill scores, targets, evidence breadth, transfer, bank/content provenance, measured changes, next actions and explicit limitations. Historical report selection preserves prior scores. Printable A4 output removes navigation and uses light paper styling.

19. **Placement dashboard improvements.** All three fictional cohorts include readiness, incomplete diagnostics, repair activity, improvement/decline/flat distributions and evidence limitations. Decision-oriented next actions guide cohort support. Seeded cohort records are explicitly fictional; no real employer validation or learner analytics are fabricated.

20. **Data Analyst regression status.** Original graph, banks, lesson content and engine remain preserved. Persistence, assessment, learning, reassessment, report, cohort and mobile/API regression journeys are included in the passing test suite.

21. **Java Developer regression status.** Original content and independent history remain preserved. Both learning modes, hints, mastery, alternate assessments, role switching, reports and fictional cohort paths remain covered.

22. **Python legacy/history compatibility.** Existing legacy assessment and lesson rows are unchanged. Legacy attempts resume through the old runner; new assessments use published authentic banks. Role histories remain independent. Historical scores are not rewritten to match the new evidence model.

23. **Security review.** Public task projections exclude answer indices, expected outputs, correct ordering, rubric keyword groups and solutions. Server-owned grading ignores client score fields. API checks ownership, active role, submission ordering and completed state; request bodies and nested outputs are bounded. Same-host write checks and HttpOnly demo cookies remain. Row locks serialize starts/submissions/completion. Hosted builds never migrate or seed a shared database. Health checks verify database/schema availability without exposing connection details. Production dependency audit found zero vulnerabilities.
